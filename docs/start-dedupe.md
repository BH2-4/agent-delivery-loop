# 共享启动资格与待确认处理

本功能由普通 Python 程序扫描、核对授权、领取和判重，再启动 Claude Worker。
它保证遵守协议的执行端对同一执行键至多启动一次；共享写入和外部 CLI
不能组成事务，因此不能承诺故障后自动推进或模型恰好执行一次。

## 身份与记录

- 执行键为规范化 JSON 数组 `[仓库小写标识, task_id, "r<revision>"]` 的 SHA-256。
  有界返修使用同一修订的明确子编号 `r<revision>/rework-1` 或 `rework-2`，
  保留现有两轮上限，不以随机请求 ID 生成新任务。
- 领取者是状态目录中持久保存的 `claimant-id` UUID；请求 ID 是每次调用的
  `run_id`；新启动记录另有 `grant_id`。三者均不改变业务执行键。
- GitHub `refs/heads/delivery-claims/<key>` 保存不可变领取记录。
  `refs/heads/delivery-starts/<key>` 保存启动记录，含领取 SHA、固定授权摘要、
  领取者、请求与 grant。内容位于该提交唯一的 `execution.json` blob。
- 领取归属只允许尝试原子创建启动记录。即使记录属于本机，也不能直接启动。
  只有本次 `POST /git/refs` 得到 HTTP 201，且响应的 ref 和 SHA 与本次候选
  完全一致，返回 `result=new, new_start=true`，才进入 CLI 预检和模型启动。
- 409/422 必须只读核对准确 ref 及有效记录；确认存在才是 `existing`。
  不存在则仍是普通校验/冲突错误。401/403、限流、不可读记录不能当作占用。
  传输故障、5xx、不可解析或不匹配的写响应为 `unknown`，禁止启动。
- 正常 Worker 回执确认后，以原启动提交为唯一父提交生成 `completed`
  记录，再用 `force=false` 快进更新。它表示 Worker 正常返回，不表示候选
  审查、PR、合并或部署已完成。原启动历史和完成记录持续保留。

直接 `agent-run` 和 `agent-watch --once` 现在需要显式 GitHub 身份；
`agent-run` 可通过 `--github-pat-file`、`--github-login` 提供细粒度 PAT，
或者消费既有编排器一次性通道；已配置且验证的 App 发布路径沿用 App 身份。
不使用环境中的日常 `gh` 凭据兜底。PAT 不传给模型。

本机文件锁、启动登记、进程组停止及 HOME 清理门禁继续生效。跨主机的
共同判断依赖同一个 GitHub 仓库及持续保留的 refs；没有租约、自动接管，
没有新增数据库、服务或后台调度器。

## 查询与人工核对

```text
agent-delivery execution-status --repo-path <repo> --execution-key <64位键> \
  --github-pat-file <仓库外私有文件> --github-login <账号>
```

此命令只读查询领取者、领取 SHA、启动 SHA、请求/grant、Worker 回执与
状态/原因，不启动模型、不修改共享记录。退出码 0 表示查询成功，不表示
任务完成。无 ref 的 `absent` 仅表示本次读取未发现 ref；执行仍必须获得
新的原子创建成功，不能把只读结果作为启动资格。

| 状态 | 含义及处理 |
| --- | --- |
| `claimed` | 已领取但未发现启动记录。只允许原领取者再次争取首次新建启动资格；其他端不自动接管。 |
| `pending_confirmation` | 启动已登记，但外部进程启动或完成回执尚未确认。后续调用不会重启。 |
| `completed` | 有正常 Worker 回执，旧请求返回已有记录，保持历史。 |
| `unknown` 返回类别 | 本次写响应无法确定；只读核对用于诊断，不能恢复本次已丢失的启动资格。 |
| 普通错误 | 认证、权限、校验、限流或记录损坏等，非零退出；不得解释为已领取。 |

待确认时依次核对：

1. 固定执行键、领取 SHA、启动 SHA 与授权摘要；保存查询结果。
2. 根据 `request_id` 找领取主机状态目录中对应 `runs/<本机任务键>/<run_id>.json`，
   核对 `execution_key`、`start_sha`、`worker_status`、`session_id` 和脱敏 `failure`。
   共享 `reason=external_launch_or_receipt_unconfirmed` 不声称进程一定已启动。
3. 在领取主机核对实际进程组、CLI 停止、候选提交、外部副作用和已有回执。
   无回执、主机不可达或 CLI 已退出，均不能单独证明没有执行。
4. 已有候选使用既有安全续接/审查流程，避免重新跑 Worker；仍无法确认则保留
   待确认。此版本不提供自动解除、接管或删除去重记录的重跑命令。

需要再执行时，必须明确批准新的 Work Order 修订（或将来明确支持的新执行编号），
保留旧记录，并承认旧执行可能已产生副作用、模型费用和重复交付。不得仅换领取者、
请求 ID、状态目录或删除 ref 来获得新的业务执行资格。

## 迁移与验收边界

旧版本的本机历史尚未自动导入 GitHub；本机保留的旧执行记录会阻止直接重跑，
但不能凭此宣称旧任务已有跨主机保护。
切换执行器前停止旧进程、保留并盘点旧状态，人工核对旧任务后只对明确的新修订
使用新入口。所有执行端均须升级；旧执行器仍能绕过新协议。

针对性产品测试映射：T1/T3 检查顺序、完成、重启重放；T2/T4 强制两个调用
实际竞争同一原子创建；T5 独立修订；T6 已写入但客户端未知，零启动；
T7 新建确认后启动前退出，零启动；T8 子进程已启动但无回执，累计一次。
产品测试中的轻量子进程不是模型；合成 API 故障不是实际网络故障。
真实 GitHub API、真实模型、CI、安装与正式部署必须分别报告证据与未验证项目。

官方 REST 语义依据：[GitHub references API](https://docs.github.com/en/rest/git/refs)。
