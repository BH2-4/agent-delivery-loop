# Agent Delivery Loop 新手术语表

这份术语表用通俗的中文，帮助刚接触 GitHub 的读者理解本项目的五个核心概念，以及一次交付要走过的人工流程。截至本文件编写时，项目仍处于早期阶段，尚未完成一次真实 Work Order 的端到端试运行，不应视为生产可用系统；下文描述的是当前设计的人工监督流程。

## 开始前的三个 GitHub 基础词

- **仓库（Repository）**：项目的文件夹加上完整的修改历史，存放在 GitHub 上。
- **分支（Branch）**：从正式版本分出来的一条独立修改线，在分支上改动不会立刻影响正式版本（通常是 `main` 分支）。
- **PR（Pull Request）与合并（Merge）**：PR 是"请审查并接纳我这条分支上的改动"的页面；合并是维护者点头之后，改动正式进入目标分支。

本项目把"批准开工"和"验收成果"设计成两张不同的 PR，就像装修前先签施工许可、完工后还要竣工验收。因此新手最需要先分清下面五个词。

## 五个核心概念

### 1. Work Order（工单）

**通俗解释**：一份机器可读的"任务授权书"。它用 JSON 格式写清楚：要做什么、不做什么、怎样算完成（验收条件）、只允许改哪些文件、什么情况必须停下。Agent 只能做工单里写明的事，不能自己扩大范围。

**本项目例子**：仓库里的 `.agents/work-orders/WO-PILOT-001-r1.json` 就是本术语表的工单——目标只有一句"新增 docs/glossary.md"，验收条件五条，允许修改的路径仅 `docs/glossary.md` 一个。你现在读到的这份文件，就是按它产生的。

### 2. Plan PR（计划 PR）

**通俗解释**：把工单放进仓库的那张 PR，相当于"施工许可申请"。它不包含实际功能代码，只包含任务授权记录及相关计划。由用户（仓库所有者）亲自点合并，才代表"我同意 Agent 按这个精确版本的计划开工"。

**本项目例子**：仓库合并历史中编号 #2 的 Plan PR（分支 `plan/wo-pilot-001-r1`），内容就是把 `WO-PILOT-001-r1.json` 这份工单加入 `.agents/work-orders/` 目录。它被用户合并后，这个任务才获得执行资格。

### 3. Delivery PR（交付 PR）

**通俗解释**：Agent 干完活之后交上来的"竣工验收单"，包含实际改动的代码、执行摘要、偏离计划之处和未解决的问题。它和 Plan PR 是两道独立的门：前者证明"可以做"，后者展示"做出来的东西"。

**本项目例子**：按 WO-PILOT-001 的流程，执行器在本地生成只包含 `docs/glossary.md` 一个文件变更的交付分支；人工检查后，由人用自己的 GitHub 身份推送该分支并创建 Delivery PR。Agent 自己不能推送、审查或合并这张 PR。

### 4. CI（持续集成）

**通俗解释**：GitHub 在 PR 上自动运行的机械检查，像一台"体检机"：能量血压（代码能不能编译）、测反射（测试过不过）、验血型（配置文件格式对不对），但看不懂"这份检查报告本身写得好不好"。CI 结果是绿的，只说明机械项通过。

**本项目例子**：本仓库的 "Minimal CI" 工作流会在 PR 上：编译 `src/` 下的 Python 源码、运行聚焦回归测试、解析 Work Order schema 的 JSON 格式，并校验示例工单。它不扫描每张新工单，也不会判断改动是否符合工单意图。

### 5. Session（会话）

**通俗解释**：Agent 的一次独立工作对话，有自己唯一的编号（Session ID）。本项目里每次执行任务都开一个全新的 Session，在独立的工作目录（worktree）中进行，不复用你平时和 Claude 交互的会话，避免不同任务之间互相"记忆污染"。

**本项目例子**：`agent-run` 启动 Claude Worker 时，会新建独立 worktree 和一个新 Session，并把本次运行与实际 Session ID 关联记录；会话内容本身不会保存或提交到仓库，只在仓库之外的本机私有状态目录留下脱敏的运行记录。

## 人工交付流程：一次交付走过的路

这个流程的关键是：每个需要"人"的环节都真的由人来做，没有任何一步被自动跳过。

1. **讨论需求**：用户与 Steward（负责规划与审查的高智力 Agent）把需求聊清楚，整理成一份工单草案。
2. **创建 Plan PR，并由用户合并**：Steward 创建包含工单的 Plan PR；只有用户本人点合并，任务才正式获得授权。
3. **人工启动 agent-run**：合并动作不会唤醒任何机器。用户在自己电脑上手动运行 `agent-run`，指明已合并的 Plan PR 和工单路径；执行器还会再次核实这张 PR 确实已合入 `main`。
4. **Claude 在新 Session 中工作**：执行器建好隔离环境，启动一个新 Session 的 Claude Worker；它只能使用受限的文件工具，只能修改工单允许的路径。
5. **生成本地交付分支**：Worker 完成修改后，执行器核对改动没有越界，在本地提交出一条交付分支；默认不推送 GitHub。
6. **人工推送并创建 Delivery PR**：用户亲自检查本地分支，确认内容后用自己的 Git/GitHub 身份推送分支并创建 Delivery PR；个人凭据不经过 Agent。
7. **CI 检查和 Codex 审查**：GitHub Actions 在 PR 上运行机械检查；同时由人启动 Codex（Steward）做独立的语义审查，向用户给出精简结论。
8. **人工决定是否合并**：用户综合 CI 结果与审查结论，决定合并、要求重跑，或关闭 PR。Agent 无权批准或合并自己的成果。

## 三个容易误解的点

- **合并 Plan PR 不等于本机自动开工**。合并只授予"执行资格"；系统没有配置定时任务，不会自动唤醒你的电脑。必须有人手动运行 `agent-run`（或 `agent-watch --once`）才会真正开始。电脑离线期间，授权一直安全地保存在 GitHub 里，不会丢失。
- **CI 不能替代语义审查**。CI 只做机械检查（编译、测试、格式解析），读不懂工单的意图；判断"改动是否真的符合授权范围、有没有越界或隐藏问题"，必须依靠 Codex 的语义审查和人的判断。两道门都要过，谁也替代不了谁。
- **合并 Delivery PR 不等于部署上线**。合并只代表改动进入 `main` 分支；本项目当前阶段不包含任何部署环节，代码合入后不会自动发布到任何线上环境。
