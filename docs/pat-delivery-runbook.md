# PAT 交付 Runbook（当前单机阶段）

本文写给本仓库的使用者，说明细粒度 PAT 身份下从只读预检到 Delivery 合并的操作顺序、门禁与失败边界。令牌的本地准备、推荐权限与预检命令细节见 [PAT 接入说明](pat-setup.md)——本文只链接，不复制任何凭据；当前阶段的身份决策见 [ADR-0007](adr/0007-fine-grained-pat-stage.md)；本 runbook 对应的固定任务规格见 [PAT Goal 模板](goal-pat-trial.md)。

全文一致使用以下两个定义，表述与 [pat-setup.md](pat-setup.md) 第 1 节及 [ADR-0007](adr/0007-fine-grained-pat-stage.md) 的“决定”与“边界澄清”一致：

- **可信 Python 控制程序**：编排器与它启动的 agent-run Python 运行器等**模型之外**的可信控制程序。PAT 模式下，GitHub 授权读取与全部写操作（推送、创建 PR、合并及写后核对）由这条控制程序边界以同一身份执行；令牌只存在于此边界内。
- **Claude 模型 Worker**：由 Claude Code 以**固定模型**驱动的模型子进程，任务输入是已授权工单与仓库工作树；其 Claude 认证只从用户确认的仓库外 settings 读取。它**不获得** PAT 令牌值、PAT 文件路径或其传递通道；独立只读审查子进程同样不获得 PAT。

不要把 `agent-run` 误认为模型 Worker：它是 Python 控制程序。凡是“不接触 PAT”的约束，指向 Claude 模型 Worker 与审查子进程等模型进程，不指向可信 Python 控制程序。

**表述约定（操作要求 ≠ 已验证能力）**：以下各节的流程与条件均为**操作要求**，描述流程应如何执行，不构成任何环节已实测通过的声明。**已验证能力**仅限证据文件记录的实测结果，只在本段单独列出，不与操作要求混写。截至 2026-10-06，证据文件记录的实测结果只有：

- 三轮限次实验（ADR-0004/0005/0006）验证了单机交付链的机械部分；当时身份是“一次性个人 gh 登录”例外，不是细粒度 PAT（ADR-0007“背景”）。
- 第四、五轮实验暴露两处实现层缺口，ADR-0007 于 2026-10-06 追加“边界澄清”予以记录，原决定不变（ADR-0007“边界澄清”）。
- 真实 PAT 接入、安装与交付尚未验证（[pat-setup.md](pat-setup.md) 状态行，2026-10-05）；`write_permissions_verified`、`protection_verified`、`delivery_verified` 保持为假，直到被真实操作逐项观察（ADR-0007“后果”）。
- 共享代理出口的匿名 GitHub 额度曾被观察到耗尽并中断链路，消耗来源未确认（ADR-0007“边界澄清”第 2 条）。

除上述证据记录外，本文不把任何规范要求表述为已实测通过。

## 预检与交付顺序

按下列顺序执行；任一步失败即按“失败停止与人工处理”停止：

1. **安装来源核对**：执行器源码须先经独立审查、合并，并按准确源码 SHA 重建普通 wheel；记录源码 SHA、wheel SHA-256 与安装回执。已安装 wheel 不随源码改动自动更新；不得用 `PYTHONPATH` 或 editable 安装冒充安装验证。
2. **只读预检**：安装后从目标仓库以安装版入口运行 `agent-delivery check-github-auth`，显式给出 `--github-pat-file <仓库外私有令牌文件>`、`--github-login <预期账号>` 和一张已有 PR（`--pr <编号>`；如本轮指定代理则按显式参数传入）。它只读核对实际账号、目标仓库、指定 PR 和 Actions 的 run／jobs 读取，不重跑任务、不启动模型。预期结果（规范值）：退出码 0、状态 `read_access_verified`，账号／仓库／PR／CI 读取字段为真。
   - **预检只读成功不能证明写权限**：`write_permissions_verified`、`protection_verified`、`delivery_verified` 在预检中为假；空检查列表不能证明 CI 通过；预检成功也不能证明推送、创建 PR、合并或令牌实际权限边界、到期日已验证。
   - 若指定对象的匹配 CI 证据已不可用，先报告，不得改选无 CI 的对象过关。
3. **写操作链**：预检通过、且 Plan PR 已实际合入 `main` 后，才由安装版 `agent-delivery deliver` 单次串联：安装来源核验 → PAT 只读预检 → 已合并 Plan PR 授权核对 → Worker 执行并捕获退出码 → 运行记录与允许范围复核 → 只读审查（必要时有界返修）→ 回执核对 → 同一 PAT 推送并定位／创建 Delivery PR → 等待该 head 的必需 CI。默认停在“待用户合并”；仅当本轮另行明确授权合并（如显式 `--auto-merge`）且下一节门禁全部满足时才合并。

真实 PAT 预检与写操作链在本阶段尚无实测记录（见开篇证据清单）。

## Plan 授权与 Delivery 审查的区别

合并 Plan PR 与合并 Delivery PR 是两个不同的决定，不能互相替代：

| | Plan PR | Delivery PR |
| --- | --- | --- |
| 回答的问题 | 是否允许开始这个固定任务 | Worker 成果是否可以合入 `main` |
| 合并的含义 | 用户对固定任务的预先授权（开工） | 质量门禁通过、成果进入 `main` |
| 合并条件 | 用户合并，或下述限次预授权例外 | 下述门禁全部满足 |

**Plan 授权**：Plan PR 是用户对固定任务的预先授权。执行器绑定该 Plan merge commit 上的工单修订与内容摘要，开工前再次核实 PR 确已合入 `main`，不信任调用方传入的状态。Plan PR 由用户合并；特定轮次用户可给出**限次预授权例外**——独立审查确认工单逐项符合用户给出的范围、未扩大目标／验收／允许路径，且其精确 head 的 CI 通过后，被授权的 Steward 可替用户以普通方式合并，偏离任一条件必须交回用户。该例外一次性、限次，不改写“Plan PR 由用户合并”的通用原则，**也不构成对后续任务、新修订或新一轮实验的自动批准**——每轮任务都需要独立的用户授权。**Worker 不批准自己的工单**。

**Delivery 审查**：Delivery PR 是 Worker 成果的质量门禁，合并前必须全部满足：

- `agent-run` 实际退出码 0，Worker 已确认停止，结构化结果为 `complete`、验收逐项核验且无未完成事项；
- 允许路径与最终提交核验通过；
- 独立审查结论为 `pass`，绑定候选完整 head；head 变化后旧审查失效，须对新 head 重新审查；
- 该 head 的必需 CI 真实成功：`ci.yml` 的 `pull_request` 运行在精确 head、固定 attempt 下全部任务成功且唯一 `validate` 成功（契约见“精确 SHA 与 CI 门禁”）；
- 远端 head 与候选一致（未漂移）；合并命令本身绑定精确 head（`--match-head-commit`）；
- 写前持久化合并意图，写后只读核对，最终确认 `main` 包含同一候选；不使用 `--admin` 等管理员绕过。

## PAT 不交给模型 Worker

- 令牌由用户在本地创建并保存为**仓库外私有文件**；只有可信 Python 控制程序读取并校验（属主与权限、单链接普通文件、细粒度 `github_pat_` 前缀、位于 Git checkout 与 Worker 状态目录之外），校验不通过即停止。
- PAT 模式下，编排链路上的授权读取（编排器自身、它启动的 agent-run 运行器、审查资料包准备与回执核验）以及推送、创建 PR、合并与写后核对，都由可信 Python 控制程序以同一身份完成；令牌在控制程序之间传递的实现细节不在本文范围。
- **Claude 模型 Worker 与独立只读审查子进程永远不获得 PAT**：不得到令牌值、PAT 文件路径或其传递通道。Worker 的 Claude 认证只来自用户确认的仓库外 settings，且固定模型、端点与 effort；认证来源与指定端点不匹配时停止，不自动切换。
- 推送与写后核对使用同一身份，不混用日常登录身份。
- 文件权限与环境清理**不等于操作系统级隔离**：同一系统用户仍可能读取文件或进程信息；本阶段未验证 OS 级边界。

## local_ready/merged/deployed 的区别

- **`local_ready`（本地结构化完成）**：命令退出码 0、运行记录为 `status: local_ready` 且 `worker_status: stopped`、实际提交与允许范围核验通过。它只表示本地候选已就绪，不代表 Delivery PR 已创建，更不代表已合入。Worker 返回结构化 `complete` 也不等于执行成功：命令非零退出时，不能凭 `complete`、本地提交或磁盘上的 `local_ready` 记录宣称本次执行成功。
- **`merged`（已合入）**：Delivery PR 在上一节门禁全部满足后实际合入 `main`，并经写后只读核对确认 `main` 包含同一候选。
- **`deployed`（已部署验证）**：**本阶段不存在该状态。** v0 不包含部署，也没有 `deployed` 信号与自动部署流程。不得把 `local_ready` 或 `merged` 称为“部署完成”；代码进入 `main` 也不等于已经部署。

## 精确 SHA 与 CI 门禁

- **审查与合并都绑定完整 40 位 head**：审查回执记录其绑定的完整 head SHA，模型回报的 SHA 还须经外层 Git／GitHub 查询核对；PR 出现新提交后旧审查自动失效，不能沿用旧结论；合并命令绑定该精确 head。
- **CI 契约**（除此之外的任何检查状态都不当作通过）：
  - 只认 `.github/workflows/ci.yml` 的 `pull_request` 运行，且必须匹配精确 head SHA、与目标 PR 不冲突；在匹配运行中选最新一个；
  - 固定该 run 的 attempt，核对该 attempt 全部任务并回读 run；
  - 工作流与全部任务成功、且唯一的 `validate` 任务成功，才通过；
  - **空检查列表不是成功**；列表不完整或超过 100 条即停止，不得漏扫后宣称通过。
- CI 核对只使用明确支持细粒度 PAT 的 Actions run／jobs 读取（`Actions:read`），不依赖 Checks API 或 `gh pr checks`，不读取外部 App checks 或 commit statuses，也不据此声称已核验全部仓库保护要求；若新增必需检查或改变工作流，必须先更新本契约再继续。

真实 PAT 身份下的 Actions 读取兼容性与 CI 核对尚无实测记录（见开篇证据清单）。

## 失败停止与人工处理

**出现以下情况立即停止对应动作**：PAT 缺失、格式不安全、失效或到期；权限不足；账号错配（实际账号与 `--github-login` 预期不符）；CI 失败、缺失或状态未知；远端结果不明（推送、PR、合并后的核对不一致）；身份或格式异常；Worker 停止未确认；范围越界或证据不匹配。

停止时的处理：

- 保留脱敏运行记录与成果，不改写状态记录，输出报告；不打印原始认证输出，不在聊天、工单或仓库中索要或写入令牌。
- 给出**最小人工配置步骤**，由用户处理后重新从只读预检开始，例如：在本地创建／续期细粒度 PAT（资源所有者与目标仓库固定、有限期限；建议权限仅 Metadata:read、Contents:write、Pull requests:write、Actions:read）并保存为仓库外私有文件；修正预期账号；在 GitHub 侧补齐仓库权限或修正目标 PR／CI 状态。
- **不换身份**：不回退日常 `gh` 登录、classic PAT 或匿名身份，不切换模型、端点或认证来源。
- **不盲目重放写操作**：推送、创建 PR、合并都是写前落意图、写后只读核对的一次性动作，失败后不得自动重放；只读请求遇瞬时传输故障按有界策略重试，限流与认证／权限拒绝立即停止。是否继续由用户决定。
