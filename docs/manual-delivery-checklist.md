# Agent Delivery Loop 人工交付检查清单

这份清单面向刚接触 GitHub 的用户，把一次人工交付拆成五个阶段，每个步骤都可以逐项勾选。它是一份操作手册，不是执行记录：勾选由用户和外部执行器（本机的 `agent-run` 等命令）逐步完成，本文档本身不证明其中任何一步已经发生。

> [!IMPORTANT]
> 截至本文编写时（2026-10-04），首次真实 Work Order `WO-PILOT-001-r1` 已经运行：Worker 返回结构化 `complete` 并生成了本地候选提交，但 `agent-run` 在最终运行记录校验时报错并以非零退出码结束，没有创建 Delivery PR，完整交付链路尚未成功。本清单描述的是其后每次交付应核验的步骤；本文档所属的工单以及任何后续工单，在用户按清单核验并合并 Delivery PR 之前，都不应被视为已经执行成功。

## 怎么使用这份清单

- 按阶段顺序勾选 `- [ ]`，尽量不要跳步：后一阶段依赖前一阶段的结论。
- 清单由用户和外部执行器核验，不要求 Worker 参与。Worker 只在受限文件工具中修改代码，不应运行清单中的命令，也无法证明自己退出之后的状态。
- 命令示例中的 `<尖括号>` 与 `/path/...` 都是需要替换的占位参数；不要把真实凭据或本机私有路径填进任何文档或提交。
- 运行状态、worktree 和运行记录存放在仓库外的本机私有状态目录，不提交到仓库。背景概念见[术语表](glossary.md)，整体流程见 [README](../README.md) 和[引导交付说明](bootstrap.md)。

## 开工前

这个阶段确认"任务确实被授权、本机确实允许开工"。任何一项不满足，先不要启动命令。

- [ ] **Plan PR 已由用户合并到目标 `main`。** 开工授权的唯一信号是用户本人把 Plan PR 合并进 `main`。PR 只是"已创建"或"正在讨论"都不算数；Steward 也不能替用户合并 Plan PR。
- [ ] **授权绑定在那次合并提交上。** 执行器会查询 GitHub，核实指定的 PR 确实已合入 `main`，然后在那次 merge commit 上读取工单、修订号、内容摘要（SHA-256）和 Delivery Skill，并固定代码基线。授权不能来自未合并的 PR、Issue、评论，或仓库里可能被再次修改的"最新版"浮动文件；`examples/` 下的示例工单本身也不构成授权。
- [ ] **确认已安装执行器的来源。** 本机执行器应来自经过审查并合并的完整 merge SHA 构建的普通 wheel，并记录源码 SHA 与 wheel SHA-256（构建与安装步骤见[引导交付说明](bootstrap.md)）；不要用来历不明或 editable 安装的版本执行工单。
- [ ] **安全门禁允许启动。** 执行器领取任务前会扫描本机全部运行记录。只要存在停止未确认（`start_unconfirmed`、`stop_unconfirmed`）、`running`、`cleanup_failed`、记录损坏或缺少安全字段的情形，就不要启动新任务，转入"失败停止"阶段由维护者人工检查。
- [ ] **理解"合并计划不会自动开工"。** 合并 Plan PR 只授予执行资格；本机没有定时器或守护进程，必须有人手动运行 `agent-run`（或 `agent-watch --once`）才会真正开始。电脑离线期间，授权一直安全地保存在 GitHub 里。

## 人工启动

这个阶段由用户在本机手动执行命令，所有运行配置必须逐项显式给出。

- [ ] **逐项显式指定配置。** 启动命令必须明确给出 Plan PR、工单路径、模型、端点、effort 和仓库外的认证配置文件，例如（尖括号与 `/path/...` 均为待替换占位符）：

  ```sh
  agent-run --plan-pr <merged-plan-pr-url> \
    --work-order-path <work-order-path-in-repo> \
    --model glm-5.3 \
    --base-url https://open.bigmodel.cn/api/anthropic \
    --effort max \
    --auth-config /path/outside/repository/claude-settings.json
  ```

  手动运行 `agent-watch --once` 时，同样必须显式提供模型、端点、effort 和认证配置四个参数。

- [ ] **本轮使用固定配置。** 当前 Worker 固定为 Claude Code CLI、模型 `glm-5.3`、端点 `https://open.bigmodel.cn/api/anthropic`、effort `max`。一次运行只使用一个固定模型和供应商，中途不切换、不降级、不做故障转移。
- [ ] **不修改 CC Switch，也不继承旧 shell 路由。** 执行器使用不可变配置快照，父环境中的旧模型、路由、认证和 effort 设置不会覆盖显式参数。不要为了让命令跑通去修改 CC Switch 配置，也不要新建 Worker 专用认证文件。
- [ ] **认证配置不一致时停止。** 模型认证只从指定的仓库外 settings JSON 的 `env` 中读取唯一一个受支持且非空的认证项，且其中的 `ANTHROPIC_BASE_URL` 必须与显式 `--base-url` 指向同一端点。若 CC Switch 当前供应商与本次目标不同、出现多个候选认证项或端点不一致：停止，由用户另行明确认证来源；不要自动切换、降级或猜测。
- [ ] **预算参数按软限制看待。** 工单中的预算数值会传给 Claude CLI，但在当前兼容端点下并未验证为真实的扣费硬上限；不要因为设置了预算就假定费用已被强制封顶。
- [ ] **确认隔离方式符合预期。** 每次执行都会创建全新的 Claude Session 和独立的 Git worktree，运行 ID 会与实际 Session ID 关联记录；不会续接你正在交互的会话，也不保存完整 transcript（Session ID 只用于关联记录，不能恢复对话）。
- [ ] **凭据不经过 Worker。** 模型认证只由执行器以受控方式注入 Worker 子进程环境；Worker 不读取认证文件，也不在文档或报告中输出认证值。个人 `gh` 凭据和 GitHub App 凭据都不传给 Worker。

## 执行结束后

命令返回后先不要推送。这个阶段要把"Worker 说做完了"和"执行器成功结束"区分开：前者只是模型返回的结构化状态，后者需要以下各项同时成立。

- [ ] **`agent-run` 退出码为 0。** 任何非零退出（校验失败、超时、Ctrl+C、异常）都表示执行器层面没有成功结束，转入"失败停止"阶段。
- [ ] **运行记录同时满足 `status: local_ready` 和 `worker_status: stopped`。** 在仓库外的私有运行记录中核对这两个字段，并确认记录中有本次运行与 Session ID 的关联。
- [ ] **实际提交内容在允许范围内。** 检查本地交付分支：变更只落在工单允许修改的路径内，提交基线与授权的 merge commit 一致（执行器在提交前后都会复核，这里由人工再确认一遍）。
- [ ] **不要把 Worker 的 `complete` 当成执行成功。** 结构化 `complete` 只代表该次模型调用报告所有验收条件满足，不等于本次执行成功。命令非零退出时，不能仅凭 Worker 返回了 `complete`、本地已有提交，或磁盘上出现 `local_ready` 记录，就宣称本次执行成功。首次真实工单就发生过这种情况：Worker 返回 `complete` 且本地已有候选提交，但执行器最终校验失败并以非零退出，完整交付链路未成功。

## 交付审查

按下面的编号顺序走。跳步容易让"检查过的版本"和"审查过的版本"悄悄变成两个不同的版本。

- [ ] **1. 人工检查本地成果和 head SHA。** 在本地交付分支上阅读实际改动，记录分支的完整 head SHA；后续所有检查和审查都应绑定这个 SHA。
- [ ] **2. 人工推送并创建 Delivery PR。** 由用户使用自己的 Git/GitHub 身份推送分支并创建 Delivery PR；个人凭据不传给 Claude Worker。当前 GitHub App 未配置、`main` 未启用保护，`--publish` 会被拒绝，默认路径就是人工推送。
- [ ] **3. 等待 CI 检查。** GitHub Actions 运行确定性机械检查（源码编译、聚焦回归、Work Order schema 与示例解析）。CI 不扫描每张新工单，也不能判断改动是否符合工单意图。
- [ ] **4. 人工启动 Codex／Steward 独立语义审查。** 审查由人手动启动，结论绑定精确 head SHA；PR 上出现新提交后，旧审查自动失效。
- [ ] **5. 由用户决定是否合并。** 用户综合 CI 结果与审查结论，决定合并、要求重跑或关闭 PR；Agent 无权批准或合并自己的成果。
- [ ] **CI 与审查必须对应同一个交付版本。** PR 上有新提交时，CI 与语义审查都要针对新的 head SHA 重新进行；不能用旧提交的绿灯或审查结论放行新版本。
- [ ] **记住两句话：CI 不替代语义审查；合并不等于部署。** CI 只做机械检查，越界、遗漏和意图偏差要靠独立审查和人判断；合并只代表改动进入 `main`，本项目当前不包含任何部署环节。

## 失败停止

出现下列任一信号时，先停止继续试运行；本阶段的勾选都应在"不再启动新任务"的前提下完成：

- 命令以非零退出码结束；
- Worker 返回 `blocked` 或 `incomplete`；
- 运行记录异常：无法读取、JSON 损坏、字段缺失或状态矛盾；
- 停止未确认：出现 `start_unconfirmed`、`stop_unconfirmed` 或 `cleanup_failed`。

- [ ] **停止，不要立刻重试。** 保留交付成果、worktree、临时 HOME 和运行记录，记下运行 ID，供维护者检查进程与状态存储。
- [ ] **报告脱敏信息。** 对外只报告脱敏后的状态、未完成事项和运行 ID；不粘贴认证值、私有路径或完整会话内容。
- [ ] **不绕过门禁。** 不得自动重试或重跑；不得改写、修补或删除运行记录；不得换用其他状态目录（例如另设 `AGENT_STATE_DIR`）绕开阻断；不得仅凭"已经过了一段时间"或"某个 PID 不存在"就判定 Worker 已停止。
- [ ] **返修需要另行明确授权。** 需要返修时，由用户明确授权并以新 Session 接入；当前没有自动续修、恢复或清除阻断的命令，`agent-run` 也不会接手原有 Delivery 分支。恢复方案须在取得独立安全确认后单独制定和审查。
