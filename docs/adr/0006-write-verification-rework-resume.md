# ADR-0006: 写结果核对、有界返修与安全续接（第三轮限次实验）

**日期**：2026-10-05<br>
**状态**：accepted（限次实验例外，experiment_id `exp-20261005-r3-1108`）<br>
**决策者**：仓库所有者（用户）与 Harness Steward

## 背景

第二轮实验（ADR-0005，Issue #18）把证据契约与只读可靠性固化进了 harness，但交付链的最后一段（返修、推送、建 PR、等 CI、合并）仍由 Steward 手动接完。暴露的缺口：

1. `GitHubClient.request()` 的读重试同样作用于 POST 写请求；推送/建 PR/合并缺少"意图先行、结果核对"的语义。
2. `changes_required` 直接中止编排；返修由人完成，返修次数没有跨中断的持久计数。
3. 基础设施失败后没有安全续接入口，只能用组件级手动操作收尾。

## 决定（本轮工程范围）

### A 写操作结果核对

- 读/写分离：只有 GET 享受分类重试；POST 等写请求单次执行，响应丢失（网络断开、5xx）一律归为 `GitHubWritePendingError`，绝不自动重放。
- `publish` 模块：每个外部写（推送分支 / 创建 Delivery PR / 合并 PR）先持久化操作意图与完整身份（仓库、任务与修订、分支、目标分支、候选 SHA、操作类型）；检查点保存失败即不执行写。
- 结果核对：写后用只读查询核对远端真实状态——已成功则接纳真实结果且不重复执行；远端明确不存在（404）才允许一次有界重试；其余歧义一律停止。合并绑定审查通过的精确 head；PR 创建复用唯一匹配。合并后核验 PR 状态与 main 包含关系。

### B 有界返修与安全续接

- `changes_required` 仅在证据明确的成果缺陷时触发返修：全新 Claude 会话（同一固定配置与 Skill，`rework_directive` 逐字携带审查发现）在原 Delivery 分支上工作，完全复用 `run_claude` 的启动登记、进程组停止、安全记录与清理机制；返修有独立 run 记录（`mode: bounded_rework`，关联原 run_id、父提交、返修轮次），原记录与原候选永不改写。
- 返修上限 2 轮，计数持久在编排记录中，跨续接累计不重置；`blocked` 不触发返修、不弱化验收；基础设施失败复用已捕获且身份匹配的 pass 回执重新核对，不重调模型。
- `agent-delivery resume --orchestration-id`：仅从已确认安全完成的阶段续接；续接前重核安装来源、授权、运行记录、候选与外部状态；不重跑原 agent-run、不恢复停止不确定的进程；参数与记录绑定不一致即拒绝。

### C 发布链由 harness 接完

`deliver`/`resume` 共用同一阶段机（install → authorization → evidence → worker → review(→rework→review) → push → PR → CI → merge → main 核验），每阶段可靠落盘检查点；`--auto-merge` 在全部门禁满足后合并。

## 本轮例外与期限

- 一次性使用现有个人 `gh` 登录态；范围仅限本轮工程 PR、Plan PR、Delivery PR 与一张跟踪 Issue 的创建/更新与门禁满足后的普通合并。
- 期限：2026-10-05 11:08 至 15:08（UTC+8）；不使用管理员绕过，不放宽仓库规则；到期仅做有界安全收尾。
- 唯一新真实工单（不重跑 WO-PILOT-001/002、WO-DOC-TRIAL-001、WO-RUNBOOK-002）；工程单元与工单各最多两轮有效返修。
- 个人 `gh` 权限可能大于本轮授权，不声称已实现硬隔离；GitHub App 长期路线（ADR-0002）不变。

## 后果

- 上两轮由 Steward 手动接完的环节进入 Python；发布链首次可由 harness 全程管理，且每个写操作的结果都有只读核对背书。
- 仍不证明：正式 App 无人值守线路、OS 级凭据隔离、真实 Claude 全部异常停止路径、账单硬上限、部署；返修与续接路径若未在真实试运行中发生，仅以回归验证为据，不称真实发生。
