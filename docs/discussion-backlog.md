## 1. Agent 在 GitHub Issue 中持续讨论项目进度

**提出日期：**2026-09-29<br>
**状态：**待讨论；不进入首轮实现。

期望 Agent 能在 GitHub 上与用户持续对齐项目进度，例如直接使用 Issue，或采用具有类似讨论与留痕能力的方式。讨论不应只存在于某台电脑的 CLI 会话里；用户应能看到当前进展、阻塞问题、需要决策的事项，以及相关 Plan PR、Delivery PR 和运行记录的链接。

后续需要讨论：

- 一个 Work Order 对应一个 Issue，还是使用项目级长期讨论 Issue？
- 哪些进展值得发评论，怎样避免心跳式刷屏和重复汇报？
- Agent 可否主动提问、回复和总结？哪些回复是资料，哪些需要人类明确决定？
- 公开仓库中如何避免泄露私有路径、凭据、完整会话和不宜公开的工作细节？
- Issue 的文字不能自动变成执行授权；Plan PR 的合并仍是当前正式开工信号。如何防止评论中的提示注入影响 Agent？

## 2. CLI 启动与常驻模式下的 Session 归属和上下文管理

**提出日期：**2026-09-29<br>
**状态：**部分基础机制已实现；首次真实 Work Order 后再讨论是否需要恢复协议。

首版每次执行创建新 worktree、随机 Claude Code Session ID 和独立 HOME，不复用交互 Session；Session ID 与 Work Order 修订、Plan merge SHA、运行 ID 记入本机权限受限的 JSON 记录。CLI 的 transcript 持久化关闭，临时 HOME 在执行后删除。因此能追踪“这次运行要求并得到哪个 Session ID”，但无法恢复或复核完整对话；这是刻意保留的未决取舍。

不论由本机定时任务启动一个 CLI 进程，还是让已启动的 CLI 通过定时任务、心跳或其他机制自动领取任务，都必须知道这次动作属于哪一张 Work Order、哪一次执行尝试、哪个 CLI Session，不能误用用户正在交互的会话或另一项任务的上下文。

讨论时应明确区分三种标识：

1. **任务身份：**已授权的 Work Order 修订和 Plan PR 合并结果。
2. **执行身份：**本次运行的唯一编号、主机、工作目录、代码基线与固定配置。
3. **会话身份：**Agent 框架实际创建或恢复的 Session ID，以及该 Session 已包含的上下文。

后续需要讨论：

- 一次无人值守任务是否总是创建新 Session？什么条件下允许恢复原 Session？
- 定时器每次启动新进程时，怎样验证所选 Session 确实属于本次任务，而不只是拿到了一个可用 Session ID？
- 常驻 CLI 或心跳模式下，怎样避免把新任务注入用户正在使用的交互 Session？
- 中断后恢复时，怎样校验 Work Order 内容摘要、仓库提交、工作目录、Agent 配置和 Session 记录一致？不一致时应如何停下？
- 各 CLI 对创建、恢复、导出 Session 的能力不同，最小通用约束应放在外部执行器，还是放在各框架适配层？
- Session 摘要应保存在哪里、保存多久，以及如何避免公开仓库泄露私人对话？

初步方向是：**不要把“当前打开的 CLI 窗口”当作任务身份，也不要仅凭 Session ID 断言上下文正确。**首轮延续“每次执行新会话、独立工作目录”的范围；是否允许可靠恢复和常驻会话，等真实运行记录出现后再做决定。

## 3. 薄启动封装：用户批准任务，工具装配执行命令

**提出日期：**2026-10-07<br>
**状态：**需求已确认；待当前 MCSociologyMock 首轮小任务试运行结果确认后再立项，暂不实施。<br>
**跟踪入口：**[Issue #37](https://github.com/BH2-4/agent-delivery-loop/issues/37)。文档发布不代表功能完成，跟踪 Issue 不因本次文档 PR 合并而关闭。

用户不应长期复制包含目录创建、权限、代理、模型、凭据路径、安装回执和版本摘要的整段 `deliver` 命令。需要保留的是任务授权与成果接纳的决策权，而不是参数装配和敲命令的劳动。

最小方向：**一份本机私有启动配置 + 一个薄启动入口**，调用现有安装版 `deliver`；每次主要提供 Plan PR 与 Work Order 引用，不另建调度平台。

- 配置保存固定模型、端点、思考程度、代理、状态目录、已批准的工具版本与凭据路径；凭据正文不得进入配置、仓库、命令参数或日志。
- 入口完成既有预检、私有审查目录创建、参数装配、启动和退出状态汇报；不削弱已合并 Plan 授权、独立会话、安全门禁、审查与 CI 检查。
- 工具版本锚点来自已批准配置，不能仅把回执中的值复制为“预期值”，也不能自动追随最新版；升级后明确更新一次配置。
- 默认不自动合并，不切换模型或改变 CC Switch 全局配置；失败不盲目重跑，不扩大任务范围。
- 只返回精简状态、运行编号、PR 链接、失败原因及下一步，不把完整会话或凭据打印出来。

后续验收重点：用户只需指定任务并批准启动，无需逐项填写长命令；实际执行仍可追溯到固定授权、配置和安装版本。此次记录不授权编写封装、安装定时器、设置自动领取或启动模型。
