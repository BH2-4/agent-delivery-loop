# 下一个迭代：模型调用前的本机任务预筛选

**状态（2026-10-15）：**提议中的下一迭代，尚未实现。当前优先完成 Claude Code CLI 原生定时唤醒下的一张真实任务交付闭环；本方案不阻塞该验证，也不代表自动预筛选已可用。

## 动机与当前证据

当前主线由每台电脑各自的本机定时任务唤醒当前 Agent，再由当前 Agent 检查共享任务并接单。用户报告已通过 Claude Code CLI 原生 Cron 创建任务 `dc636fba`，计划为 `7,37 * * * *`，创建响应当时给出 next run `23:20`。用户还报告进程退出后任务不再触发、任务七天到期。现有记录只证明 Cron 创建成功；尚无证据证明后续自动唤醒实际发生或已完成新任务。按会话型使用，不从这些信息推断额外的持久化或恢复能力。

空扫的成本问题是：若每次定时唤醒都先调用模型，再由模型扫描共享状态，那么没有新任务的轮次仍会消耗模型 token。目标是在受支持的入口存在时，让本机普通程序先做只读筛选；没有值得处理的候选时，不调用模型。有候选时，仍由宿主支持的方式唤醒当前 Agent。

## 必须保持的边界

- 各电脑继续各自调度；不引入中央调度器、后台服务、跨电脑唤醒，也不由 Codex 或接入件启动第二个 Agent。
- 预筛选只决定是否值得唤醒模型，不构成任务授权或执行许可。醒来的 Agent 仍须按 Skill 核对 `show`、`status` 和能力匹配；只有本轮 `acquire` 明确返回 `can_execute=true` 才能执行。
- `pending_confirmation`、`pending_gate`、`unknown`、错误或副作用状态不自动重试、不接管、不重报；遵守现有“只读核实后停止”规则。
- 设计需处理并发唤醒、候选积压和重复事件，避免为同一候选重复唤醒或让一个会话并行领取；不新增租约或自动接管语义。

## 首要研究问题与最小步骤

1. 核实当前 Claude Code CLI 版本是否提供受支持的“模型调用前筛选”入口，以及在有候选时把事件送入并唤醒当前会话的受支持方式。以实际 CLI 和官方支持资料为准；Cron 提示词里再加脚本仍会先唤醒模型，不能据此声称消除了空扫 token。Monitor、Channels 等候选能力在核实前不视为可用方案。
2. 若存在受支持入口，选用最小的本机只读筛选，按共享任务状态合并或去重唤醒事件。若不存在，记录阻塞和可行边界，不以不受支持的私有接口替代。
3. 只做一次真实反馈验收：没有可执行新候选时，确认预筛选没有调用模型；出现一张已授权且能力匹配的新任务时，确认当前 Agent 被唤醒，并仍经 `show`、`status`、`acquire` 完成任务和回执。待确认或状态未知时确认流程停止。

验收后再决定是否继续采用该入口。范围不含部署服务、切换到 Desktop、扩展任务协议或新增大规模测试套件；Claude 主线真实任务闭环可独立继续。
